## 一、目标与验收定义

### 1.0 一句话目标

> 把制度问答从**"检索一次就作答"的开环**，升级为**"会判断证据够不够、能主动补齐、不够就明确拒答"的闭环**；
> 在多跳 / 枚举汇总 / 条件+例外 这几类问题上提高**证据覆盖度与拒答正确率**，同时**保证简单事实题不退化**。

### 1.1 定位：目标不是"提高检索准确率"

"提高检索准确率"是**另一条路**——换更好的 embedding、加 rerank、调分块、混合检索权重，都属于在**单轮之内把检索做得更好**。Agentic RAG 改的是**形态**：

> 普通 RAG 优化的是「**一次检索的质量**」；Agentic RAG 优化的是「**检索质量不可控时的决策与兜底**」——它不假装召回永远够，而是把"不确定性"从**糊弄过去**变成**显式处理**。

### 1.2 四个目标能力（按企业场景价值排序）

| 目标                  | 对应痛点                                         | 单轮管线为什么做不到                                        |
| --------------------- | ------------------------------------------------ | ----------------------------------------------------------- |
| **证据覆盖度**        | "公司对 X 有哪些规定"这类枚举/汇总，答案散在多章 | 窗口是固定 `top_k` 截断，且合并子问题后直接砍尾，天然收不全 |
| **充分性判断 + 拒答** | 文档没有 / 写得不全时，必须敢说"没有"            | 检索完直接生成，模型只能编或糊弄                            |
| **多跳 / 条件+例外**  | "入职不满一年的年假怎么算"这类条件组合           | 一次检索只覆盖一个事实点                                    |
| **可审计**            | 答案要能指到**具体条款**、出错能归因到哪一步     | 只有一次检索，没有决策痕迹                                  |

**对企业知识库（合规 / HR / 制度问答）而言，后三项比"多答对两道事实题"值钱得多**——所以 InsightForge 的面试口径是：

> 价值不在"答对一道事实题"，而在 **① 敢说"文档里没有"（合规场景不能编）；② 把散在多章的规定收齐；③ 答案能指到具体条款、可核对可审计**。

### 1.3 验收指标（分层，不能只看总分）

| 维度       | 指标                                                                  | 为什么                                         |
| ---------- | --------------------------------------------------------------------- | ---------------------------------------------- |
| 有效性     | 多跳/枚举题的**关键词收全率**、`source_count`/章节覆盖数              | 总分里单点事实题占多数，会掩盖 agentic 的收益  |
| **安全性** | **拒答正确率 / 无据作答率**（该说"文档没有"时有没有说）               | 企业场景最硬的需求，也是最容易被忽略的指标     |
| 效率       | 平均步数、P95 延迟、token 增量；**简单事实题延迟增幅上限**（如 ≤50%） | 没有护栏的 agent 上线即退化                    |
| 可归因     | Langfuse 多步 trace（thought / tool / retrieve 各一个 span）          | 出错能定位到"检索没召回 / 判断错了 / 生成编了" |

### 1.4 不是 demo 的判定标准（三条都得满足）

1. 改动点由**基线失败数据**指出来，不是我拍脑袋；
2. 每个能力上线**挂评估数据**（同评估集、同口径、baseline vs agent）；
3. 简单事实题**延迟/成本不劣化**（有直答快路径与预算上限）。

### 1.5 边界：什么时候**不该**用 agentic

- 单点事实查询（本集 16/22 是这类）：走直答快路径，多轮只会更慢更贵；
- 纯编号定位（"第三十六条是什么"）：已由**确定性元数据过滤**解决（`5ff4b22`），不需要 agent 决策；
- **反直觉但必须承认**：若只以准确率论英雄，agentic 在企业知识库上常**打不过**一个调好 rerank 的单轮管线 —— 这也是为什么这套系统要以"覆盖度 + 拒答 + 可审计"为目标，而不是以"准确率"为目标。

## 二、现状事实盘点（2026-09-15 在本机实测，可复核）

**管线**（部署镜像 2026-08-28 构建）

```
check_injection → 语义缓存(阈值 0.92) → QueryDecomposer(LLM 拆 2~4 子问题)
→ CompositeRetriever(dense+bm25+summary → RRF k=60, fetch×3 ≤30)
→ 按 chunk.id 去重 → 截断 top_k → Generator(每 chunk 只喂 500 字, max_tokens 600)
→ compute_confidence（关键词启发式）
```

- LLM 只出现在两处：**问题改写**（query_decomposer）与**生成回答**（generator）。检索、融合、去重、置信度均无 LLM。
- `LLMGateway.generate()` 只透传 `messages/max_tokens/temperature/stream`——**没有 tools / tool_choice / JSON mode**（M2 的 function calling 需要先扩这里）。
- `HybridRouter`（BM25 规则路由）存在但未接入主链路；`summary` 路检索的 24 篇**文档级摘要**已入库但只当第三路召回用。

**语料**：`chartermate_docs` 912 chunks（dim 1024 / COSINE）+ `chartermate_summaries` 24 篇（= 24 份文档的摘要索引）。

**评估**：core 服务 `/core/eval`（评估集 CRUD + 跑批 + 看板），评估集「员工手册-恒大」22 题，判分 = 关键词命中 + 章节匹配。

- 最新 run#7（2026-08-29）：**18/22 = 81.8%**，均分 0.871，类别分布：

| 类别     | 题数 | 均分     |
| -------- | ---- | -------- |
| 事实查询 | 16   | 0.917    |
| 概念查询 | 2    | **0.50** |
| 理解推理 | 1    | 1.00     |
| 综合概括 | 3    | 0.833    |

- 失分点：**T008「十六字方针」= 0**、**T015「第三十六条是什么内容」= 0**、T022「新员工入职后应该了解哪些制度」= 0.5、T001 = 0.667。
- **评估集结构性缺陷**：16/22 是单点事实查询（73%），真正考验多步的「理解推理 + 综合概括」只有 4 题 → **当前评估集测不出 agentic 的价值**，扩题必须先做。
- 缓存/延迟口径：`/v1/stats` 显示语义缓存命中率 74.6%；run#7 记录 29.5s/题、run#6 记录 0.29s/题 → 后者疑似缓存命中轮。**跑对比前必须先锚定口径（use_cache=false，评估服务已是这么调）**。

## 三、哪些点值得 agentic（按 ROI 排序）

排序依据：基线失分位置 + 该场景在制度问答里的真实频次。

**P0-1 条款/编号定位**（对应 T015=0）

- 现象：问「第三十六条是什么」，语义检索对纯编号几乎无信号，命中的是"讲第三十六条**附近内容**"的段落。
- 根因：条号是**结构化属性**，被当成普通文本做向量检索。
- 改法：新增工具 `lookup_clause(条号/章节号)`，走结构化精确命中（元数据/BM25 加权），agent 在"问题含编号"或"语义检索低分"时调用。
- 指标：条款类题通过率、`chapter_match` 命中率。

**P0-2 证据充分性判断 + 补检索**（这是最本质的 agentic，也是当前最大空白）

- 现象：检索一次定生死，无论召回是否覆盖问题，直接进生成；不足时模型只能编或答"未找到"。
- 根因：管线是**开环**的（decompose 一次 → retrieve 一次 → generate）。
- 改法：闭环 = 检索结果 → 充分性判断（缺什么）→ 改写/换工具再检索 → 汇聚；最多 N 轮，超限降级。
- 指标：低分题是否被补回、平均步数、P95 延迟、token 增量。

**P0-3 枚举/汇总类**（对应 T022=0.5、T021 弱）

- 现象：「新员工入职后应该了解哪些制度」这类要收齐散落在多份文档的清单项，top_k=3~10 的窗口天然收不全。
- 根因：证据窗口是**固定 top_k 截断**，且合并子问题后 `[:top_k]` 直接砍掉后面的子问题的证据。
- 改法：`gather` 工具——先用 24 篇文档摘要定位"哪些文档相关"，再逐文档取相关段，**覆盖度记账**（缺哪篇补哪篇）而不是拼 top_k。
- 指标：综合概括类均分、`source_count`/文档覆盖数。

**P1-4 多文档对比**（HR/合规真实高频，当前评估集没有这类题）

- 现象：「《员工手册》和《考勤制度》对请假的规定有什么不同」→ 需要按文档分组、按维度对齐，现有检索只有 chunk 级排序。
- 改法：`compare_docs(文档A, 文档B, 维度)` 工具：按文档分别取证 → 对齐维度生成。
- 指标：新增对比题通过率（依赖扩题）。

**P1-5 答案把关（proposer-critic）**

- 现象：生成后无校验，引用完整性/是否越界编造没人管（prompt 里要求"引用来源"，但无检查）。
- 改法：生成前/后加一次校验（信息是否足以支撑结论、引用是否落在证据里），不通过 → 回退补检索或重写。
- 指标：无据作答率（人工抽检 + 关键词判分）、引用可核对率。

**P2-6 原生 function calling + Langfuse 多步 trace 树**

- 工具化是形态升级（M2），M1 先用**严格 JSON 动作输出**降低风险；Langfuse 已全面接入，多步 trace 树是展示与归因的地基。

### 反面清单（明确不做，防过度设计）

- ❌ 多 Agent 编排/角色扮演协作——24 份文档的问题域用不上，只加调试成本。
- ❌ 用 LLM 替换 BM25 规则路由——现有 `HybridRouter` 够用，收益低。
- ❌ 会话记忆 / 追问澄清——二期，真实痛点未验证。
- ❌ 前端 UI 改造——API + curl 演示足够。
- ❌ **让简单事实题也走多轮**——这是最容易把项目做"贵"的地方；必须有直答快路径 + 步数/延迟预算。

## 四、M1 落地设计（最小侵入）

- 只加新模块，**不动 Core / Doc-Kit**：`docs_seeker/agent/`
  - `agent_loop.py`——ReAct 循环：思考 → 选工具 → 观察 → 充分性判断 → 生成或继续（步数上限 3）
  - `tools.py`——工具注册表，M1 只上两个：`search_docs`（复用 `CompositeRetriever.search`）、`lookup_clause`
  - `sufficiency.py`——充分性判断（M1 用一次 LLM 调用 + 结构化输出，失败回落"认为充分"）
- **开关可逆**（沿用"保留原方案 + if/else"）：请求体加 `mode: baseline|agent`，默认 `baseline`；agent 分支失败/超预算 → 自动回退原管线。
- **缓存**：agent 模式不写/不读现有语义缓存（或把 mode 并入缓存键），避免单轮缓存答案污染对比。
- **流式**：`chat_stream` 先只保证 baseline；agent 走非流式（或仅最后一步流式），不引入 SSE 复杂度。
- **预算护栏**：MAX_STEPS=3、单问 token/延迟上限、超限降级。
- **Langfuse**：一次问答 = 一棵 trace 树（thought / tool / retrieve 各一个 span）。

## 五、评估设计（先做，且要能证伪）

1. **扩题 +12**（在现有 22 题基础上，沿用 `case_id/category/expected_keywords/expected_chapter` schema，经 `/core/eval` 的评估集 API 导入）：
   - 多跳 4 题（跨条款/条件+例外，如"入职不满一年的年假怎么算"）
   - 对比 4 题（两份文档同一维度的差异）
   - 枚举 4 题（"公司对 X 有哪些规定"类，答案可列举核对）
   - **出题前提**：每题先在语料里核对确有答案 + 不跨文档超纲（防止出偏题）。
2. **三组对比**：同评估集、`use_cache=false`、同 top_k，跑 baseline vs agent；指标：总分、类别分、通过率、平均步数、平均延迟、token（Langfuse 取）。
3. **反例保护**：简单事实题的延迟增幅设上限（例如 ≤50%），超了就得加快路径，而不是发数据。
4. **纪律**：「验证再写」——数据没跑出来前，简历/README/口头故事一个字不加。

## 七、风险

- **概念类失分可能不是检索问题**：T008「十六字方针」= 0 需先核对语料里是否有这句、是否被 chunk 切断——若是语料/切分问题，agentic 治不了，要如实写进结论。

- **口径漂移**：历史 run 存在缓存命中轮（0.29s/题），对比前必须锁 `use_cache=false`，否则数据不可比。

## 八、拉代码后的实测补充（2026-09-15 晚，含语料抽样证据）

代码已拉到 `/opt/datapilot`（主仓库）+ `services/docs-seeker`（GitHub 镜像 main `83ab3b9`）。抽检语料（Zilliz `chartermate_docs`，只读）后发现**三个确定性缺陷，优先级高于 agentic 改造**：

**① 语料重复入库：912 chunks = 228 唯一内容 × 4 份完全相同的副本**

- 4 个 source（`tmp*.pdf`）两两内容指纹交集 = 并集 = **100%**，全库唯一指纹只有 228，重复分布 = 全部 ×4。
- 影响：top_k 窗口被同一段落的 4 份副本互相挤占 → 枚举/汇总（T022/T021）与条款定位（T015）在窗口里根本装不下别的证据；这也解释了评估报告里老是 `source_count=3`。
- 去重只按 chunk.id（uuid），**没有内容级去重防线**。
- 结论：**不修这个，agentic 的多步检索只会重复取回同样的 4 份副本，对比数据不可信。**

**② 结构化元数据齐全，但完全没参与检索**

- 覆盖率（912 chunks 实测）：`chapter` 98%、`chapter_title` 98%、`section` 89%、**`article` 80%**（取值如「第一条」「第四项」「第1款」，条/项/款混装）。
- `chapter_title` 里就有「员工行为规范（**简称"十六字方针"**）」（56 chunks）和「员工修身准则（**简称"三十六条"**）」（224 chunks），而 `article == '第三十六条'` 有 8 chunks。
- 但检索只有 dense/BM25/summary 三路语义召回，**article/chapter/section 从未进入过滤或加权** → T008（十六字方针）、T015（第三十六条）双双 0 分，根因是「元数据没接线」，不是「不够 agentic」。
- 结论：`lookup_clause` 类能力在**数据层已具备条件**，属于低成本确定性修复，agentic 只是它的调用方之一。

**③ BM25 命中在 /chat 里被静默去重掉**（STATUS.md P2-12 仍在）

- `MilvusStore.get_all_documents` 的 `output_fields` 没有 `id` → BM25 的 chunk 无 id → `rag_pipeline.prepare` 按 `chunk.id or ""` 去重时全部归并成一条，BM25 召回几乎全丢。
- 结论：这是「证据静默丢失」，和充分性闭环（P0-2）是同一根因链条，**应先修**。

**由此修正执行顺序**（原方案第三节的 ROI 排序不变，但前置一层）：

| 顺序 | 内容                                                | 理由                               |
| ---- | --------------------------------------------------- | ---------------------------------- |
| 0    | 清重复语料 + 内容级去重防线                         | 不修则所有对比数据不可比           |
| 1    | 元数据接线（article/chapter 过滤或加权）            | 确定性提分，直接命中 T008/T015     |
| 2    | 修 BM25 去重坍缩（补 id / 内容哈希兜底）            | 静默丢召回，同样是确定性修复       |
| 3    | 再上 agentic（充分性闭环 + lookup_clause + gather） | 前三步做完，agentic 的增量才可归因 |

**语料侧限制**：`docs` 集合实际只有 **1 份唯一文档**（228 chunks），所以原方案里的「多文档对比」在当前语料上**做不了**——要么先补第二份文档，要么把对比题改成「同一文档不同章节对比」。

## 九、本地环境就绪 + 又发现一个 P0（2026-09-15 夜）

**本地环境**：`.env` 从部署目录复制（`/opt/datapolit-docs-seeker/.env` → 项目根，600 权限，`.gitignore` 已忽略）。

- Milvus（Zilliz 云）连通：`row_count = 912` ✅
- Redis：容器 **未映射宿主机端口**，且实例是生产数据（`rag:usage:*` 等）。本地默认在 `.env` 末尾加 `SEMANTIC_CACHE_ENABLED=false`（避免污染生产缓存/统计）；需要测缓存时改 `REDIS_URL=redis://172.18.0.6:6379/0`。
- 端到端跑通：`POST /v1/chat`（stream=false, use_cache=false）→ 200，检索命中、LLM 正常调用。

**P0（新）：推理模型 + 小 `max_tokens` → 两处 LLM 调用都返回空内容**

- **两处都中招**，不只是一处：
  1. **答案生成** `generator.generate / generate_stream`：`max_tokens=600`。实测问 T008 → `finish_reason=length`、`reasoning_content` 977 字、`content` **0 字**（空答案）；提到 3000 → `finish=stop`、正常输出 351 字。

**结论（三条，分开记）**：

1. **延迟是真实增量** ✅ —— 同 workers 下 agent 比单轮快 **1.7~2.9×**（P95 快 1.4~2.0×），两轮一致。归因假设：单轮路径的**查询改写**是延迟大头（推理模型 + 2000 token 预算），而 agent 只做一次 500 token 的短超时决策；agent 平均 2.97 步（2 步 ×16、3 步 ×5、4 步 ×3、5 步 ×6）。
2. **准确率无增益** —— agent 27~28 vs 单轮 28~29（均分 0.922~0.978 vs 0.972~0.983）。不构成退步（噪声带内），但**不能记为提升**。§12 期待的"换表述检索补 T23 类召回缺口"**部分成立**（T23 两轮都从 0.5 翻到 1.0），但被 T15/T27 的失分抵掉。
3. **稳定性是 agent 当前的主要短板** ⚠️ —— 比总分更值得看：
   - `T15`（法国站 UIN）：**两轮都 0.667**，两轮都漏同一关键词 `代您准备申报报告`，单轮稳定 1.0 → **稳定短板，不是噪声**；
   - `T27`（TikTok 佣金，域外拒答）：**r2 被硬编成答案**（拒答 4/4 → 3/4）→ 两段式裁决的终态不够稳；
   - `T07`（r1 0.667 → r2 1.0）、动作解析失败（r1 为 T20/T26、r2 为 T13，均自纠成功）→ 属偶发噪声。
