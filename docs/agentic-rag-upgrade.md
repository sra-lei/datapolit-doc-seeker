# InsightForge Agentic RAG 升级方案（2026-08-27 定稿）

> 决策背景：用户主攻 AI 应用/RAG/Agent 岗，Agent 无落地作品（理论多、未上手输出）。选定路径 A：把 InsightForge 的 Docs-Seeker 从「单轮检索问答」升级为「Agent 循环问答」，产出可演示、可量化评估的 Agent 作品。

## 目标

1. 补 Agent 岗简历缺口：一个真 Agent 案例（开源 + 可演示 + 有评估数据）
2. 延续评估驱动叙事：Agentic vs 普通 RAG 的数据对比
3. 面试故事连贯：RAG → Agentic RAG 是行业演进主线

## 设计原则

- **最小侵入**：只加 agent 模块，复用现有检索 / Milvus / 评估集 / Langfuse，不动 Core 和 Doc-Kit
- **评估驱动**：每个能力上线必须挂评估数据，拒绝"感觉变好了"
- **演示优先**：M1 起 API 可 curl 演示，不憋大招

## 能力集（按价值排序）

1. **多步检索（自纠错检索）**：首轮检索信息不足 → LLM 分析缺失信息 → 改写/拆解查询 → 二次检索 → 汇聚答案。解决复杂问题一次检索不够
2. **工具调用（DeepSeek function calling）**：注册工具表 `search_docs` / `doc_summary` / `filter_by_metadata` / `compare_docs`
3. **多文档对比生成**：对比类问题拆解为多路检索 + 对比生成——企业知识库最痛的场景，也最出彩的 demo
4. **提议者-审核者质量保障（proposer-critic，用户 2026-08-27 提出）**：Agent 产出最终答案前，审核者校验信息充分性 / 引用完整性 / 与问题对齐，不通过则触发再检索或重写，保证完成度与完成质量——这是区别于玩具 Agent 的设计亮点，也是面试深挖点
5. （二期，先不做）会话记忆 / 追问澄清

## 架构改动（落在 Docs-Seeker）

- 新增 `agent/` 模块：
  - `agent_loop.py` — ReAct 循环（用户手写过 ReAct，正好上手）：推理 → 工具调用 → 信息充分性判断 → 生成或继续
  - `tools.py` — 工具注册表，内部复用现有 `retriever.py` 检索能力
- Langfuse：多步 trace 树，每步（推理/工具调用/检索）一个 span——叙事从「一次问答一条 trace」升级为「一次问答一棵 trace 树」
- 一期不做会话持久化、不做前端 UI 入口（API + 演示脚本即可）

## 评估设计（关键，你的招牌）

- **扩展评估集**：新增「多跳/对比类」问题 10-15 题（跨文档、对比差异、需多步检索才能答）
- **三组对比**：同一评估集上跑 Baseline RAG vs Agentic RAG，重点看多跳类通过率
- **看板加「问题类型」维度**（现有维度：事实查询类置信度）
- 预期叙事：复杂问题类通过率 X% → Y%（以真实数据为准，不预填）

## 里程碑

| 阶段 | 内容 | 周期 |
|---|---|---|
| M1 | ReAct 骨架 + 多步检索工具，API 跑通 | 3-5 天 |
| M2 | function calling + 多文档对比 + 多跳评估集（10-15 题） | 3-5 天 |
| M3 | 对比评估跑完（Agentic vs RAG）+ Langfuse 多步 trace 展示 + README/部署更新 | 3-5 天 |

## 简历/面试产出（等真实数据再落笔）

- 简历 bullet 候选：「Agentic RAG 升级：多步检索 + 工具调用，复杂问题（多跳/对比类）评估通过率 X%→Y%」
- 口头故事：RAG→Agentic 演进 + 「embedding 升级→准确率提升」同款因果链
- 开源：更新 sra-lei/datapilot 仓库（README 加 Agent 能力说明）

## 风险/注意

- **别过度设计**：Agent 复杂度 = 调试成本，先 2-3 个工具跑通再扩
- **评估题要可人工验证**：对比类题目答案要能核对，别出偏题
- **数据口径**：多跳评估数据出处要能说清，沿用「验证再写」原则——数据没跑出来前，简历一个字都不加
